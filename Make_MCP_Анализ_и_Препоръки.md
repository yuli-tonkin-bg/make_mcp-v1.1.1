# Анализ и препоръки за Make MCP сървъра

**Цел на документа:** анализ на реалните затруднения, срещнати при изграждането на проекта "AI Консултации с Юли", произтичащи от ограничения достъп на Claude до Make.com през MCP сървъра (собствен проект на Николай Стоянов). Изследвани и потвърдени от официалната Make API документация конкретни възможности за разширяване.

**Дата:** 30.07.2026

---

## 1. Обобщение на проблема

През целия проект Claude разполага само с:
- **Четене** на списъци сценарии, изпълнения, data store записи
- Няколко тесни write-действия: старт/стоп на сценарий, retry на заседнало (DLQ) изпълнение, add/delete на data store запис

**Липсва напълно:** достъп до самата структура на сценариите (модули, параметри, филтри, връзки между модули) — нито за четене, нито за писане.

**Последствие:** всяка техническа промяна (добавяне на модул, смяна на поле, добавяне на филтър условие) минава през дълъг ръчен цикъл:

1. Claude диагностицира с ограничени данни
2. Дава точни клик-по-клик инструкции на потребителя
3. Потребителят изпълнява — но Make интерфейсът има няколко объркващи изгледа (Version history срещу Execution history, Grid срещу canvas изглед), затова невинаги намира точното място от първия път
4. Праща скрийншот
5. Claude се преориентира и дава следваща стъпка
6. Цикълът се повтаря, често 5-10 пъти за едно концептуално просто действие

**Конкретни примери от проекта:**
- Добавяне на forced tool_choice схема в HTTP модул (Prompt 1) — цял диалог само за да се пейстне текст
- Добавяне на Router модул с 2 филтъра (по statusCode) — отне много стъпки заради объркване кой елемент точно да се кликне
- Диагностика на "[400]" грешка от Speechmatics — часове разследване, защото нямаше начин директно да се види реалната стойност на масива `download[]`, който Vimeo е върнал
- Клониране и препрограмиране на Basecamp error-handler модули
- Грешно свързан Router клон (модул случайно закачен на грешния маршрут) — открито едва след няколко скрийншота

## 2. Потвърдени възможности на Make API (официална документация)

Изследването потвърждава: Make има пълноценен REST API, покриващ точно нужните възможности. Ето потвърдените ендпойнти:

### 2.1 Структура на сценария (най-важното)

| Метод | Path | Какво прави |
|---|---|---|
| GET | `/scenarios/{scenarioId}/blueprint` | Връща пълната JSON структура на сценария — всички модули, параметри, филтри, връзки |
| PATCH | `/scenarios/{scenarioId}` | Обновява blueprint (като JSON), scheduling, име, папка |
| POST | `/scenarios` | Създава изцяло нов сценарий |
| DELETE | `/scenarios/{scenarioId}` | Трайно изтрива сценарий |
| POST | `/scenarios/{scenarioId}/clone` | Клонира сценарий (копие за безопасно тестване) |
| POST | `/scenarios/{scenarioId}/restore` | Възстановява изтрит сценарий (30-дневен прозорец) |

**Това е точно същият механизъм, който самият Make UI ползва зад кулисите, за да покаже canvas-а.** Тоест не е нужно нищо ново да се "измисля" в Make — само по-широк набор от MCP wrapper инструменти около вече съществуващото API.

### 2.2 Изпълнения и диагностика

| Метод | Path | Какво прави |
|---|---|---|
| GET | `/scenarios/{scenarioId}/executions/{executionId}` | Детайли на конкретно изпълнение, вкл. per-module input/output данни (нужна е допълнителна проверка колко дълбоко навлиза спрямо plan tier-а) |
| POST | `/scenarios/{scenarioId}/replay` | Повторно изпълнение на КОНКРЕТНО минало изпълнение (не само DLQ) |
| GET | `/scenarios/{scenarioId}/interface` | Вход/изход спецификация на подсценарий (напр. C-то ни, което приема transcript/item_id/ime_klient) |
| PATCH | `/scenarios/{scenarioId}/interface` | Промяна на входните спецификации на подсценарий |

### 2.3 Заседнали изпълнения (DLQ) — пълен набор

| Метод | Path | Какво прави |
|---|---|---|
| GET | `/dlqs` | Списък заседнали изпълнения |
| GET | `/dlqs/{dlqId}` | Детайли (метаданни, НЕ реалните данни) |
| **GET** | **`/dlqs/{dlqId}/bundle`** | **Реалните данни (bundle), които са били обработвани в момента на провала** — точно каквото ни трябваше вчера за диагностика на Speechmatics 400-грешката |
| GET | `/dlqs/{dlqId}/blueprint` | Blueprint-ът на сценария в момента на провала |
| DELETE | `/dlqs` (bulk, с `confirmed=true`) | Изтриване (потвърдихме и ползвахме вчера индиректно) |
| POST | `/dlqs/{dlqId}/retry` | Повторен опит |

### 2.4 Връзки (Connections)

| Метод | Path | Какво прави |
|---|---|---|
| GET/POST | `/connections` | Списък / създаване на нова връзка |
| POST | `/connections/{id}/test` | Проверка дали credentials-ите още са валидни |
| POST | `/connections/{id}/set-data` | Обновяване на данни на връзка |

Потвърдено: връзки могат да се създават програмно и за не-OAuth типове (API ключове), не само през браузър флоу.

## 3. Препоръчани нови MCP инструменти (по приоритет)

### Приоритет 1 — Бърза, ниско-рискова победа
**`make_get_blueprint(scenario_id)`** — read-only, обвива `GET /scenarios/{id}/blueprint`. Само това би премахнало около половината от вчерашното забавяне (цялото "screenshot-ни ми какво има сега в това поле"), без никакъв риск за живите сценарии.

**`make_get_dlq_bundle(dlq_id)`** — read-only, обвива `GET /dlqs/{dlqId}/bundle`. Директен достъп до истинските данни зад провалено изпълнение — точно каквото ни трябваше за диагностиката на Speechmatics бъга вчера, без часове UI археология.

### Приоритет 2 — Контролирано писане (с потвърждение преди действие)
**`make_update_blueprint(scenario_id, blueprint_json)`** — обвива `PATCH /scenarios/{id}`. Позволява директно създаване/промяна/свързване на модули. **Най-високата стойност, но и най-високият риск** — виж раздел 4.

**`make_delete_dlq(dlq_id)`** — обвива `DELETE /dlqs/{dlqId}` или bulk варианта. Директно чистене на заседнали изпълнения, без ръчно търсене на чекбокс + плаваща лента в интерфейса.

**`make_clone_scenario(scenario_id)`** — обвива `POST /scenarios/{id}/clone`. Позволява автоматизирано "работи на копие, тествай, после смени" — вече установен като добра практика в проекта.

### Приоритет 3 — По-рядко нужни, но стойностни
**`make_replay_execution(scenario_id, execution_id)`** — обвива `POST /scenarios/{id}/replay`. Различно от DLQ retry — може да презапусне ВСЯКО минало изпълнение (не само провалено), полезно при случаи като "осиротелия транскрипт" от 29.07 (реален webhook получен, но обработката спряна заради несъответствие).

**`make_get_scenario_interface` / `make_update_scenario_interface`** — за преглед/промяна на входните полета на подсценарии (като C).

**`make_create_connection`** — за нови интеграции без ръчно UI преминаване.

## 4. Важно за баланса — риск срещу полза

Изследването на официалните препоръки за MCP (Model Context Protocol) сървъри с write достъп потвърждава точно модела, който Николай предложи:

> *"Enforce least privilege by defaulting to read-only tools and enabling write/edit tools behind explicit roles and policies... requiring approvals for high-risk operations."*

Тоест: работният модел "Claude предлага план → одобрение → Claude действа" **не е компромис, а официално препоръчаната практика** за точно тази ситуация — не маха контрола на потребителя, само мести физическото изпълнение от неговите ръце в Claude-овите, докато решението остава негово.

**Допълнителни препоръки от изследването, приложими тук:**
- **Прогресивно ниво на достъп:** започни само с read-only инструменти (Приоритет 1), добавяй write достъп постепенно, модул по модул, докато се натрупа доверие
- **Работа на копие за структурни промени:** за по-съществени промени — клонирай сценария (`make_clone_scenario`), направи промяната на копието, тествай, чак тогава смени живия — прилагайки точно принципа "рефактор на копие, не на живия сценарий", вече established в проекта за други идеи
- **Строга валидация на входа:** тъй като blueprint-ите са сложен вложен JSON, всяка промяна, предложена от Claude, трябва да мине през JSON валидация ПРЕДИ изпращане към Make API (аналогично на вече доказаната практика в тази сесия — валидиране на JSON текст чрез PowerShell преди paste)
- **Одит/лог на действията:** всяко write действие да оставя следа (кога, какво точно е променено) — полезно ако нещо се обърка, за бързо връщане назад

## 5. Отворени въпроси за проверка (преди имплементация)

1. **Дълбочина на execution logs API-то** — нужна е директна проверка (не само търсене) дали `GET /scenarios/{id}/executions/{executionId}` реално връща per-module bundle данни за ВСИЧКИ типове изпълнения (не само DLQ), или изисква по-висок Make план (Enterprise tier). Това пряко определя дали общата диагностика (не само за провалени/DLQ случаи) може да стане директна.
2. **API token scope** — текущият Make API токен, ползван от MCP сървъра, има ли изобщо write scope към blueprint-и, или трябва нов токен с разширени права?
3. **Кой Make план е активен** — някои от тези ендпойнти (особено детайлни execution logs) може да са ограничени до определени тарифни планове.

---

## 6. Заключение

Изследването **потвърждава** първоначалния анализ — Make API-то напълно поддържа нужните възможности, вече е публично документирано, и не изисква нищо извън стандартна REST интеграция. Препоръчителен ред на изграждане:

1. Добави `make_get_blueprint` + `make_get_dlq_bundle` (read-only, нулев риск) — веднага усеща голямо намаляване на забавянето
2. Тествай известно време само с тях
3. Добави `make_clone_scenario` + `make_delete_dlq` (ниско-рискови write действия)
4. Едва тогава обмисли `make_update_blueprint` — с изричния "план → одобрение → действие" модел, и предпочитание за работа върху клонинг при съществени промени

## 7. П3 — ресърч и рискове (добавено 30.07.2026, след изграждане и живо тестване на П1+П2)

П1 и П2 (и ниско-рисково, и високо-стойностно) са изградени, release-нати и потвърдени на живо (виж `HANDOFF.md` раздел 2). Преди да продължи към П3, направен е допълнителен ресърч в Make community форума и официалната документация за всеки от трите инструмента — резултатът промени първоначалната преценка за реда/готовността им. **Решение на 30.07.2026: П3 се оставя на пауза**, докато не се реши да продължи.

### 7.1 `make_replay_execution` — риск: среден, с реална неясноta около основната му цел

- Официалната документация потвърждава endpoint-а (`POST /scenarios/{id}/replay`), но с документиран капан: **приема масив от execution ID-та, но реално replay-ва само първия**.
- Директен въпрос към Make community "може ли да се replay-не УСПЕШНО (не DLQ) изпълнение" — точно основната причина да построим инструмента (напр. случая с Промпт 2, връщащ `json: "null"`, но статус 200 — не е в DLQ). **Make support не потвърдиха, че работи** — предложиха заобиколен ръчен път (изтегли bundle, симулирай наново) вместо да потвърдят native replay за успешни изпълнения.
- Реални последствия при извикване: пуска цялата верига пак (пише в Google Docs, Monday board) — същите живи ефекти като вече съществуващия `make_run_scenario`.

### 7.2 `make_get_scenario_interface` / `make_update_scenario_interface` — риск: среден-висок, най-слабо доказан от трети страни

- Почти липсват community следи за конкретно тази операция.
- Свързан намерен проблем: "Custom App: Scenario Still Shows Old Module Schema After Update" — след промяна през API, схемата понякога остава стара/несинхронизирана за други модули/сценарии, които я ползват.
- За under-scenario interface (напр. модула „C", приемащ transcript/item_id/ime_klient) това означава реален риск от тихо счупване на сценарии, извикващи го по старата сигнатура.

### 7.3 `make_create_connection` — риск: среден, но най-добре документиран

- Намерен детайлен, работещ пример от друг разработчик (стъпка по стъпка, вкл. OAuth flow).
- Ключово ограничение: **OAuth връзки (вероятно Google Drive/Docs, Monday) не могат да се създадат изцяло програмно** — нужен е човек да завърши авторизацията в браузър; природата на OAuth не позволява друго. Инструментът реално би помагал само за **API-key** връзки (напр. Speechmatics).
- Документирани бъгове: новосъздадени връзки понякога временно невидими в списъка; OAuth полета понякога празни след създаване.

### 7.4 Препоръчан ред, ако/когато П3 продължи

1. `make_create_connection` — най-добре доказан от трети страни (макар ограничена реална полезност — само API-key типове).
2. `make_replay_execution` — работи документирано, но тествай внимателно дали покрива успешни (не само DLQ) изпълнения, преди да разчиташ на него за основния use case.
3. `make_update_scenario_interface` — последно; най-малко доказан, най-висок риск от скрито счупване на извикващи сценарии.
